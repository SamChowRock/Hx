# 后端权威性、信任边界与状态归属

> [返回教程首页](../README.md) · [本模块目录](README.md)

## 2.5 第一个思维转换：后端是权威，不是“另一个前端数据层”

前端负责把一个用户的意图表达成良好交互；后端负责决定这个意图是否可以成为所有用户共享的持久事实。

| 维度     | 前端常见处境                   | 后端必须面对                                        |
| -------- | ------------------------------ | --------------------------------------------------- |
| 运行位置 | 用户设备，可刷新、可篡改       | 受控服务器，但有多个实例和版本                      |
| 状态范围 | 一个页面、Tab、设备或用户      | 所有用户共享的业务事实                              |
| 信任     | 前端代码和请求都可被攻击者修改 | 只有服务端验证后的身份、规则和数据可信              |
| 生命周期 | 页面关闭即可丢失局部状态       | 数据可能保留数年，需要迁移、备份、删除和审计        |
| 并发     | 常关注一个用户内的异步交互     | 多用户、多设备、重试和 Worker 同时修改同一事实      |
| 失败     | 展示错误、重试请求             | 还要判断操作是否已提交、能否安全重试、如何恢复      |
| 发布     | 新前端可整体刷新               | 新旧 API 实例、Worker 和 Schema 可能同时存在        |
| 安全     | 防 XSS、保护交互               | 还要防越权、注入、CSRF、SSRF、Secret 泄漏和数据滥用 |

例如前端提交：

```json
{
  "organizationId": "org-a",
  "ownerUserId": "user-123",
  "role": "OWNER",
  "createdAt": "2020-01-01T00:00:00Z",
  "name": "My project"
}
```

后端不应照单全收：

- Actor 来自有效 Session，不来自 `ownerUserId`；
- 是否能在 org-a 创建，来自 Membership Policy；
- Role 不能由创建 Project 的请求指定；
- `createdAt` 由数据库生成；
- 只接受用例真正允许的 `name`。

这就是为什么 HTTP DTO 不能等于 Prisma Model，也不能让前端提交完整数据库对象。

## 2.6 信任边界：所有进入后端的数据都先视为不可信

不可信输入不仅是 Body：

```text
Body / Query / Path / Header / Cookie
第三方 OAuth/OIDC 回调
Webhook
Worker Event Payload
对象存储中的文件
环境变量
数据库里由旧版本写入的 JSON
管理员导入文件
```

边界校验分四层：

1. **形状校验**：是不是 UUID、Enum、合法长度；
2. **身份校验**：请求代表哪个 Actor；
3. **权限校验**：Actor 能否在这个 Tenant 对这个 Resource 执行 Action；
4. **业务校验**：资源状态是否允许，例如已完成 Task 能否删除。

Zod 只解决第一层。通过 Zod 的 `organizationId` 仍然可能属于其他租户；格式正确不等于有权限。

服务端自己生成或推导这些值：

- Actor ID；
- 租户权限；
- 创建/更新时间；
- 密码 Hash；
- Session/CSRF/一次性 Token；
- 审计 Actor；
- 价格、折扣、权限等级等权威计算结果。

## 2.7 状态应该放在哪里

前端开发常自然地把状态放进组件、Store 或浏览器存储；后端最重要的设计题之一是决定每类状态的权威位置。

| 位置           | 性质                           | 本项目中的例子                             | 可以丢吗                    |
| -------------- | ------------------------------ | ------------------------------------------ | --------------------------- |
| 函数局部变量   | 单次调用临时状态               | 已 Parse 的 Body                           | 请求结束就丢                |
| 进程内存       | 单实例、重启即失、多实例不共享 | Worker 的 `pollPromise`、密码并发计数      | 只能放协调/优化状态         |
| PostgreSQL     | 持久、事务化、可约束           | User、Membership、Project、Session、Outbox | 不能随意丢，是事实来源      |
| Redis Cache    | 快、TTL、允许淘汰              | 未来的 Project 查询缓存                    | 必须允许完全丢失            |
| Queue Redis    | 等待处理的操作状态             | 未来 BullMQ Job                            | 不应因 Cache 淘汰而丢失     |
| Object Storage | 大 Blob、流式访问              | 未来上传文件                               | 需要生命周期、备份和授权    |
| Secret Manager | 受控 Secret                    | 生产 AUTH_SECRET、Provider Credential      | 不进入代码、日志或普通表    |
| 应用日志系统   | 可检索运行证据                 | Request/Error Log                          | 不是业务事实或 Audit 替代品 |

一个实用判断法：

```text
进程重启后它能丢吗？
两个 API 实例必须看见同一值吗？
它是否参与业务不变量？
是否需要事务、查询、审计、备份或保留期？
数据量和访问模式是什么？
```

如果答案是“重启不能丢、所有实例必须一致、参与规则”，通常应先考虑 PostgreSQL，而不是类字段或本地文件。
