# 09｜PostgreSQL 生产运维、备份恢复与高可用

> [返回本模块目录](README.md)
>
> 目标：不只会“把数据库跑起来”，还要知道它什么时候正在走向故障、数据丢失后如何恢复，以及副本、高可用和备份分别解决什么问题。

---

## 1. 先建立生产数据库的责任模型

开发环境里，只要 `docker compose up` 后能连接，数据库似乎就已经“可用”。生产环境中的可用至少包含五层含义：

1. **能连接**：客户端可以建立连接并完成认证；
2. **能正确执行**：查询结果正确，事务隔离符合业务要求；
3. **能在负载下执行**：连接数、CPU、内存、磁盘 I/O 没有失控；
4. **故障后能恢复**：机器、磁盘或人为操作出问题后，数据能恢复；
5. **恢复时间可接受**：恢复过程没有超过业务允许的停机时间。

因此，数据库运维不是“DBA 才需要知道的命令”，而是对以下问题建立可验证的答案：

- 现在发生了什么？
- 为什么变慢了？
- 数据最多可能丢多少？
- 服务多久可以恢复？
- 恢复方案是否真的演练过？

---

## 2. 连接为什么是一种昂贵资源

PostgreSQL 采用“一个客户端连接对应一个后端进程”的模型。连接并不是一个几乎免费的 JavaScript 对象：每个连接都会占用进程、内存和调度资源。

### 2.1 连接池的作用

应用不应为每个 HTTP 请求新建数据库连接，而应复用连接池：

```text
HTTP 请求 ─┐
HTTP 请求 ─┼─> 应用实例内的连接池 ─> PostgreSQL 后端连接
HTTP 请求 ─┘
```

连接池同时承担两个职责：

- 避免反复建立 TCP、TLS 和认证连接；
- 给数据库施加背压，防止瞬间并发全部涌入 PostgreSQL。

“池越大吞吐越高”通常是错的。查询最终仍受 CPU 核数、磁盘 I/O 和锁竞争限制。过大的池只会让更多查询同时争夺相同资源，增加上下文切换和尾延迟。

### 2.2 先做连接预算

假设：

- PostgreSQL 的 `max_connections = 200`；
- 为管理员、迁移、监控和事故处理预留 30 个；
- 生产最多扩容到 10 个 API 实例；
- 每个实例还有普通请求池和后台任务池。

那么应用可用预算只有：

```text
200 - 30 = 170
170 / 10 = 每实例最多约 17 个连接
```

如果每个实例默认开 20 个连接，一扩到 10 个副本就已经超额。容量规划必须按“最大实例数 × 每实例池大小”计算，而不是只看单实例。

### 2.3 连接池满时发生了什么

池满不代表请求一定失败。一般流程是：

1. 请求向池申请连接；
2. 没有空闲连接时进入等待队列；
3. 已运行查询归还连接后，等待者才能继续；
4. 超过池等待超时后，请求才失败。

这意味着数据库慢查询会沿着连接池传播为 API 排队。应同时观察：

- 活跃连接数；
- 空闲连接数；
- 等待池连接的时间；
- 查询执行时间；
- HTTP 请求总耗时。

### 2.4 PgBouncer 解决什么问题

当应用实例很多、连接短暂，或使用弹性/Serverless 计算时，可以在应用和 PostgreSQL 之间加入 PgBouncer：

```text
许多客户端连接 -> PgBouncer -> 较少的 PostgreSQL 连接
```

常见池模式：

| 模式        | 后端连接何时归还 | 特点                             |
| ----------- | ---------------- | -------------------------------- |
| session     | 客户端断开时     | 兼容性最好，复用率最低           |
| transaction | 事务结束时       | 常用，但不能依赖连接级会话状态   |
| statement   | 每条语句后       | 限制最多，通常不适合普通事务应用 |

使用 transaction pooling 时要审查：临时表、会话级 `SET`、监听通知、连接级 advisory lock、prepared statement 等行为是否依赖固定后端会话。

## 3. 超时是系统边界，不只是性能参数

没有超时的等待意味着资源可以无限期被占用。

常见超时包括：

- **连接超时**：多久连不上数据库就放弃；
- **池等待超时**：多久拿不到连接就失败；
- **`statement_timeout`**：单条语句最多执行多久；
- **`lock_timeout`**：等待锁最多多久；
- **`idle_in_transaction_session_timeout`**：事务开启但没有继续执行多久后终止；
- **HTTP 请求超时**：客户端愿意等多久。

它们需要形成自外向内的时间预算。例如：

```text
上游请求超时 5s
  └─ 本服务处理预算 4s
       └─ 数据库 statement_timeout 2s
            └─ lock_timeout 500ms
```

如果 HTTP 客户端 3 秒已经放弃，而数据库查询仍运行 30 秒，系统就在为一个无人等待的结果继续消耗连接和 I/O。

## 4. 生产中应该观察什么

监控的目标不是收集尽可能多的图表，而是能够解释四类问题：可用性、延迟、流量和饱和度。

### 4.1 当前会话与长查询

```sql
SELECT
  pid,
  usename,
  application_name,
  client_addr,
  state,
  wait_event_type,
  wait_event,
  now() - query_start AS query_age,
  now() - xact_start AS transaction_age,
  query
FROM pg_stat_activity
WHERE datname = current_database()
ORDER BY query_start NULLS LAST;
```

重点识别：

- 长时间运行的查询；
- `idle in transaction` 会话；
- 大量等待锁的会话；
- 某个应用版本突然制造的大量连接。

注意：`idle` 只代表连接当前没有执行语句，不等于异常；`idle in transaction` 则意味着事务和快照仍被保留，通常更危险。

### 4.2 数据库整体活动

```sql
SELECT
  datname,
  numbackends,
  xact_commit,
  xact_rollback,
  blks_read,
  blks_hit,
  temp_files,
  temp_bytes,
  deadlocks
FROM pg_stat_database
WHERE datname = current_database();
```

不要把某个比率孤立地当作健康结论。例如缓存命中率高并不证明没有慢查询；它可能只是因为全表扫描的数据也被缓存了。

### 4.3 表和索引

```sql
SELECT
  relname,
  seq_scan,
  idx_scan,
  n_live_tup,
  n_dead_tup,
  last_autovacuum,
  last_autoanalyze
FROM pg_stat_user_tables
ORDER BY n_dead_tup DESC;
```

```sql
SELECT
  relname,
  indexrelname,
  idx_scan,
  pg_size_pretty(pg_relation_size(indexrelid)) AS index_size
FROM pg_stat_user_indexes
ORDER BY idx_scan ASC, pg_relation_size(indexrelid) DESC;
```

`idx_scan = 0` 不意味着可以立即删除索引。它可能服务于低频但关键的管理任务，也可能统计刚被重置。删除前要结合完整业务周期、约束用途和查询记录判断。

### 4.4 推荐建立的核心告警

- 实例不可连接；
- 连接使用率逼近预算；
- 长事务或 `idle in transaction`；
- 锁等待和死锁增加；
- 磁盘空间不足或增长异常；
- WAL 产生速度异常；
- 副本延迟超过业务阈值；
- autovacuum 长期未运行或 dead tuples 激增；
- 备份失败、归档失败；
- 最近一次成功恢复演练过期。

最后一项很重要：备份任务成功，只证明“写出了一些文件”，并没有证明这些文件能够恢复。

## 5. 备份、高可用和副本不是同一件事

### 5.1 三者解决的问题不同

| 能力       | 主要解决                               | 不能单独解决                     |
| ---------- | -------------------------------------- | -------------------------------- |
| 备份       | 误删、逻辑损坏、历史版本恢复、灾难恢复 | 自动快速切换                     |
| 流复制副本 | 主机故障、读扩展、较快切换             | 误删和错误更新；错误也会复制过去 |
| 高可用编排 | 故障检测、选主、流量切换               | 历史数据恢复                     |

如果有人在主库执行 `DROP TABLE`，流复制会忠实地把这次删除传给副本。副本不是备份。

### 5.2 RPO 与 RTO

- **RPO（Recovery Point Objective）**：最多允许丢失多长时间的数据；
- **RTO（Recovery Time Objective）**：事故发生后，最多允许多长时间恢复服务。

例子：

```text
RPO = 5 分钟：最多接受最近 5 分钟的数据丢失
RTO = 30 分钟：必须在 30 分钟内恢复服务
```

RPO/RTO 是业务决策，不是数据库团队单方面选择。它直接决定备份频率、WAL 归档、同步复制、跨区域部署和成本。

## 6. 逻辑备份与物理备份

### 6.1 逻辑备份：`pg_dump`

逻辑备份把表结构和数据导出为可重新执行/恢复的逻辑内容。

```bash
pg_dump \
  --host=localhost \
  --port=5432 \
  --username=scaffold \
  --format=custom \
  --file=scaffold.dump \
  scaffold
```

恢复到一个新数据库：

```bash
createdb --host=localhost --port=5432 --username=scaffold scaffold_restore
pg_restore \
  --host=localhost \
  --port=5432 \
  --username=scaffold \
  --dbname=scaffold_restore \
  --clean \
  --if-exists \
  scaffold.dump
```

优点：

- 可以按数据库、schema、表选择；
- 较适合跨版本迁移；
- 容易检查对象清单；
- custom/directory 格式支持并行恢复。

局限：

- 大库导出和恢复较慢；
- 不提供任意时间点恢复；
- 全量恢复时间可能无法满足较短 RTO；
- 全局角色等对象需要额外用 `pg_dumpall --globals-only` 处理。

### 6.2 物理备份与 WAL 归档

物理备份复制 PostgreSQL 数据文件，再持续保存 WAL。恢复时：

1. 还原一个基础备份；
2. 重放之后归档的 WAL；
3. 在目标时间、LSN 或事务点停止重放；
4. 启动为新的数据库实例。

这就是 PITR（Point-in-Time Recovery，时间点恢复）的基础。

它适合大规模数据库和严格 RPO，但要求管理：

- 基础备份周期；
- WAL 归档是否连续；
- 备份与 WAL 的保留策略；
- 加密、跨区域副本和访问权限；
- 恢复所需 PostgreSQL 主版本和扩展；
- 完整的恢复自动化与演练。

只保存基础备份而没有对应 WAL，无法恢复到备份之后；只保存 WAL 而没有可用基础备份，也没有重放起点。

### 6.3 存储快照

云盘或文件系统快照速度很快，但必须保证一致性。不能把“随手复制正在变化的数据目录”当成有效备份。应使用数据库/存储平台明确支持的一致性快照流程，并确认 WAL 与多磁盘卷的一致点。

## 7. PITR 如何处理误操作

假设 14:03 有人误删数据，期望恢复到 14:02:59：

```text
最近基础备份
    +
基础备份之后的连续 WAL
    ↓
在隔离的新实例重放到 14:02:59
    ↓
校验数据
    ↓
选择：切换整个实例 / 只导回误删数据
```

不要直接覆盖仍在运行的主库。通常应先恢复到隔离环境，因为你需要：

- 验证目标时间是否正确；
- 验证 schema、扩展、角色和数据完整性；
- 分析错误影响范围；
- 决定整体切换还是局部回填；
- 保留事故现场用于审计。

时间点恢复依赖可靠时钟和清晰的事故时间线，因此数据库、应用日志和审计事件的时间同步也属于恢复能力的一部分。

## 8. 复制、读副本与一致性

### 8.1 异步复制

主库提交成功时，WAL 可能还没有到达副本。

优点：主库提交延迟较低。缺点：主库突然永久损坏时，尚未复制的事务可能丢失。

### 8.2 同步复制

主库提交需要等待指定同步副本确认 WAL。

优点：可降低故障切换时的数据丢失。缺点：网络和副本状态会进入写请求延迟路径；配置不当时，副本不可用可能阻塞提交。

“同步”也需要进一步定义确认级别：只写入远端内存、刷入磁盘，还是已经在副本可见，并不是一回事。

### 8.3 读副本延迟带来的业务问题

典型问题：

1. 用户提交创建订单，写入主库；
2. 页面立即刷新，但读取被路由到副本；
3. WAL 尚未重放，用户看不到刚创建的订单。

这违反了用户期望的“read your writes”。可选策略包括：

- 写入后的短时间内强制读主库；
- 返回写入结果，不立即二次查询；
- 记录提交 LSN，等待副本追上后再读；
- 只把允许陈旧的查询分流给副本；
- 产品上明确展示数据同步状态。

副本扩展的是特定读负载，不会消除主库写入瓶颈，也不会自动让所有查询变快。

## 9. 故障切换为什么比“提升副本”复杂

一次安全切换至少要解决：

1. 如何确认旧主库真的失效，而非网络分区；
2. 哪个副本最新；
3. 如何确保同一时刻只有一个主库；
4. 客户端如何发现新主库；
5. 旧主库恢复后如何避免再次接受写入；
6. 其他副本如何跟随新主库；
7. 丢失了哪些事务，如何向业务解释。

如果网络把节点分成两边，而两边都认为自己是主库，就会产生 split-brain。防止它通常需要仲裁、租约或 fencing（隔离旧主）机制。

因此高可用工具的价值不只是执行 `promote`，而是管理完整的故障状态机。

## 10. 权限与角色设计

生产应用不要使用数据库超级用户。推荐至少拆分：

| 角色            | 用途               | 典型权限                             |
| --------------- | ------------------ | ------------------------------------ |
| owner/migration | 管理 schema 与迁移 | 创建、修改对象                       |
| app_runtime     | API 日常运行       | 必需表的 SELECT/INSERT/UPDATE/DELETE |
| readonly        | 报表、排障         | 只读查询                             |
| backup          | 备份任务           | 完成备份所需读取权限                 |
| monitoring      | 监控               | 统计视图读取权限                     |

为什么迁移角色和运行角色要分开？

- SQL 注入或应用漏洞无法直接 `DROP TABLE`；
- 平时运行的服务不需要 DDL 权限；
- 审计记录更容易区分应用写入与运维变更。

权限设计要覆盖未来对象的默认权限，否则新建表可能没有授予运行角色，或意外对公共角色开放。

## 11. 日常维护不是定时“优化”

### 11.1 VACUUM 与 ANALYZE

- autovacuum 回收可复用空间、防止事务 ID 回卷问题；
- analyze 更新统计信息，帮助规划器估算行数；
- 长事务会阻碍旧版本回收；
- 大批量更新后可能需要更积极的维护参数。

不要把 `VACUUM FULL` 当成日常清理。它会重写整张表并取得强锁，适合经过评估的特殊场景。

### 11.2 索引维护

索引膨胀、损坏或结构变化可能需要 `REINDEX`。生产操作要评估锁影响，优先使用支持并发的方式，并确认额外磁盘空间。

### 11.3 主版本升级

PostgreSQL 数据目录不能随意由另一个主版本直接启动。主版本升级常见方式：

- `pg_upgrade`；
- 逻辑导出/导入；
- 逻辑复制到新集群后切换；
- 托管平台提供的升级流程。

升级计划还要检查扩展兼容、驱动和 ORM 兼容、查询计划变化、回滚路径和停机窗口。

## 12. 恢复演练：备份真正有效的验收标准

至少定期完成一次恢复到独立环境的演练，并记录：

1. 找到正确备份和所需 WAL 花了多久；
2. 恢复过程花了多久；
3. 数据库能否正常启动；
4. migration 历史、扩展、角色是否完整；
5. 核心表行数和约束是否正确；
6. 应用能否用生产等价权限连接；
7. RPO/RTO 是否达标；
8. 哪些步骤仍依赖个人记忆。

恢复验证不能只做 `SELECT 1`。应有业务级检查，例如：

- 最近一批订单是否存在；
- 关键账户余额是否满足不变量；
- 唯一约束和外键是否存在；
- 最近迁移是否已应用；
- 随机抽样的附件、事件和审计记录能否对应。

## 13. 本地实验：逻辑备份与隔离恢复

> 只对本项目的本地开发数据库执行。不要把示例中的主机、数据库名直接用于共享或生产环境。

### 13.1 创建一条可识别数据

先通过 API 或 Prisma Studio 创建一条带有唯一标记的数据，例如：

```text
restore-drill-2026-08-14
```

### 13.2 创建 custom-format 备份

如果 PostgreSQL 运行在 Compose 中，可以在容器内执行：

```bash
docker compose exec -T postgres \
  pg_dump -U scaffold -d scaffold -Fc \
  > /tmp/scaffold-restore-drill.dump
```

这里的 `scaffold` 来自当前项目 `docker-compose.yml`。如果你改过数据库名或用户，需要同步调整。重定向发生在宿主机，所以备份文件位于宿主机 `/tmp`。

### 13.3 恢复到新数据库

```bash
docker compose exec -T postgres \
  createdb -U scaffold scaffold_restore_drill
```

```bash
docker compose exec -T postgres \
  pg_restore -U scaffold -d scaffold_restore_drill --clean --if-exists \
  < /tmp/scaffold-restore-drill.dump
```

### 13.4 验证

进入新数据库，检查：

- 唯一标记的数据存在；
- 表、索引、约束存在；
- Prisma migration 表与原库一致；
- 使用只读账号时不能修改数据；
- 记录完整恢复耗时。

### 13.5 清理

确认不再需要后，只删除这次实验创建的数据库：

```bash
docker compose exec -T postgres \
  dropdb -U scaffold scaffold_restore_drill
```

不要用删除整个 Docker volume 的方式代替精确清理，因为那会同时删除原开发数据库。

## 14. 事故排查的最小顺序

当数据库告警或 API 大面积超时时，建议按以下顺序建立事实：

1. **确认影响**：完全不可连接，还是部分查询慢；
2. **确认最近变化**：发布、迁移、流量、批任务、基础设施事件；
3. **检查饱和度**：连接、CPU、内存、磁盘空间与 I/O；
4. **检查活动**：长事务、锁等待、异常查询；
5. **检查复制和 WAL**：副本延迟、归档失败、WAL 激增；
6. **先止血**：暂停制造问题的任务、限流、回滚应用流量；
7. **谨慎终止会话**：先确认 PID、事务和业务影响；
8. **保留证据**：查询、指标、日志和时间线；
9. **恢复后复盘**：把临时人工判断转成监控、约束或自动化。

不要一看到慢就重启数据库。重启会消除现场信息、触发缓存冷启动，并且无法解决错误查询、连接风暴或磁盘不足等根因。
